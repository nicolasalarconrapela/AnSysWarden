# AnSysWarden i18n / Multilanguage

AnSysWarden supports English and Spanish user-facing output on the `feat/i18n-es-en` branch.

## Supported languages

- `en` — English (default)
- `es` — Español

## Persistent configuration

The recommended way to choose a language is the persistent user configuration:

```bash
./ansys config language es
./ansys config language en
```

Inspect the current configuration with:

```bash
./ansys config show
./ansys config path
```

By default AnSysWarden stores the user configuration in:

```text
~/.ansyswarden/config.json
```

Example:

```json
{
  "schema": "ansyswarden.config.v1",
  "language": "es"
}
```

PC and mobile have independent local configuration files. This is intentional: the PC may use Spanish while the mobile worker uses English, or vice versa, without changing any API contract.

A custom config location can be selected with:

```bash
export ANSYSWARDEN_CONFIG_FILE=/custom/path/config.json
```

## Language priority

When more than one language source is present, the priority is:

```text
--lang en|es
    ↓
ANSYSWARDEN_LANG
    ↓
~/.ansyswarden/config.json
    ↓
en (default)
```

This means the persisted configuration is the normal daily setting, while `--lang` is useful as a temporary one-command override.

## CLI override

You can temporarily select the language globally with `--lang`:

```bash
./ansys --lang en doctor
./ansys --lang es doctor
```

The option may also appear at the end of a command:

```bash
./ansys test e2e --backend http://127.0.0.1:8787 --lang es
```

You may also override the persisted language through the environment:

```bash
export ANSYSWARDEN_LANG=es
./ansys test safety
```

or:

```bash
export ANSYSWARDEN_LANG=en
./ansys test safety
```

## PC ↔ mobile

Use the language setting independently on each device.

PC example:

```bash
./ansys config language es
./ansys backend serve --host 0.0.0.0 --port 8787
```

Mobile example:

```bash
./ansys config language es
./ansys worker mobile --backend http://PC_IP:8787
```

The language setting affects human-readable output only. It does not change the API contract.

## Never translated

The following values are protocol and safety contracts and must remain stable in every language:

```text
SAFE_CACHE
REVIEW_REQUIRED
USER_DATA
```

The same applies to:

- API endpoints such as `/api/ai/jobs`
- schema identifiers such as `ansyswarden.ai-job.v1`
- JSON field names
- environment variable names
- machine-readable error codes such as `UNAUTHORIZED`

This keeps PC/mobile interoperability independent of the display language.

## Current localization scope

Localized user-facing surfaces include:

- `./ansys --help`
- persistent language configuration
- AI start/stop/status/test/model management
- doctor
- classify
- scan
- inspect
- PC backend startup
- mobile worker
- Dust CLI
- deterministic rule tests
- overlap tests
- AI-tree policy tests
- project-context tests
- AI candidate tests
- AI safety test output
- cache benchmark output
- model comparison / mobile-model comparison output
- PC → mobile Gemma → PC E2E test

Dynamic technical evidence returned by Gemma or stored in prior artifacts may still be in the language in which it was generated. This does not affect the safety contract.

## Validation

Run both language modes after pulling the branch:

```bash
bash -n ./ansys
npm run typecheck
npm run test:i18n

unset ANSYSWARDEN_LANG
./ansys config language es
./ansys config show
./ansys test rules

./ansys --lang en test rules

./ansys config language en
./ansys test overlap
```

Benchmark and model comparison output can be checked independently without changing their safety semantics:

```bash
./ansys --lang es test benchmark --offset 0 --limit 3
./ansys --lang en test benchmark --offset 0 --limit 3

./ansys --lang es test mobile-models --timeout-ms 15000
./ansys --lang en test mobile-models --timeout-ms 15000
```

For the cross-device path, run the worker and E2E test with independently configured languages; the machine-readable result contract must remain identical.
